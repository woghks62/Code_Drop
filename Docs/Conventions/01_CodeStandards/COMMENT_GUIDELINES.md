> 개발자(사용자)가 코드를 작성할 때 따르는 주석 컨벤션.
>
> Claude는 이 문서로 코드를 작성하지 않으며, 기술 문서 작성·검수와 힌트 제시의 근거로만 참조한다.

## 01. 기본 원칙

- 코드만으로 이유를 알기 어려운 경우에만 주석을 작성한다.
- 이름만으로 역할이 명확하면 주석을 생략한다.
- 주석은 한국어로 작성한다. 단, 코드에 나오는 이름과 Unity 용어(`Rigidbody`, `Awake`, Raycast 등)는 영어 그대로 쓴다.
- 주석은 존댓말 없이 명사형(~함, ~제외 등)으로 끝내고 마침표를 찍지 않는다. 여러 문장이면 줄을 바꿔 나눈다. `///` XML 주석도 같다.
- 주석은 항상 설명하는 코드 바로 위에 작성한다.
- 주석은 짧게 작성하고, 복잡한 설계 배경이나 긴 설명은 별도 문서에 작성한다.

## 02. 주석 종류별 작성 기준

### 02-1. 일반 주석 (`//`)
- 동작을 적지 않고 그 이유만 작성한다.
- 예외 처리, 특수한 제약 조건, 복잡한 계산의 이유 등을 설명한다.

### 02-2. XML 문서 주석 (`///`)
- 다른 클래스나 팀원이 사용하는 공개 API 중 설명이 필요한 곳에 작성한다.
- 내부 구현용 private 메서드에는 기본적으로 작성하지 않는다.
- `summary`에는 해당 API의 목적과 역할을 간결하게 작성한다.
- `param`, `returns`는 작성하지 않고, 필요한 설명은 `summary`에 함께 적는다.
- 호출 조건, 부작용, 예외 사항 등 사용자가 알아야 할 계약을 우선 설명한다.

### 02-3. TODO / FIXME 주석
- `TODO`, `FIXME` 주석은 작성하지 않는다.
- 남은 작업이나 버그는 GitHub Issue로 관리한다.

### 02-4. 코드 구분 및 영역 주석
- 필드, 프로퍼티, 메서드 등의 단순 구분을 위한 주석은 기본적으로 작성하지 않는다.
- 코드의 배치 순서는 `CODE_STYLE.md` 01-5를 따른다.
- 파일이 길거나 기능별 구분이 필요한 경우 간결한 영역 주석을 사용할 수 있다.
- 장식용 구분선이나 반복적인 영역 주석을 남발하지 않는다.
- `#region`은 사용하지 않는다.
- 예외: 아래 영역의 시작 위치에는 구분선 주석을 반드시 작성한다.
  - 다른 클래스에서 사용하도록 공개한 멤버(`public`) 영역. 범위를 한눈에 알 수 있도록 영역의 시작과 끝에 같은 구분선을 작성해 감싼다. 시작 구분선은 XML 문서 주석(`///`)보다 위에, 끝 구분선은 마지막 멤버 바로 아래에 작성한다.
    - 공개 프로퍼티: `// -------------------------------------- 공개 프로퍼티`
    - 공개 이벤트: `// -------------------------------------- 공개 이벤트`
    - 공개 메서드: `// -------------------------------------- 공개 메서드`
  - 초기화 메서드(`CacheComponents` 등, `CODE_STYLE.md` 01-5의 10번): `// -------------------------------------- 초기화`
  - 에디터 디버그용 메서드(`OnDrawGizmos` 등, `CODE_STYLE.md` 01-5의 11번): `// -------------------------------------- 씬 확인용`
  - 해당 메서드가 여러 개여도 구분선은 영역 맨 위에 한 번만 작성한다.
  - 끝 구분선 작성 기준: 영역 바로 뒤에 구분선이 없는 코드가 이어지면 끝에도 구분선을 작성한다.
    - 공개 멤버 영역 뒤에는 구분선이 없는 생명주기 메서드나 private 메서드가 이어지므로 끝 구분선으로 범위를 표시한다.
    - 초기화, 씬 확인용 영역은 뒤에 다른 구분선이 오거나 클래스가 끝나 범위가 드러나므로 시작 구분선만 작성한다.
- 영역 주석이 많아지면 클래스의 책임 분리가 필요한지 검토한다.

### 02-5. 임시 주석 처리된 코드
- 개발 및 디버깅 과정에서 코드를 임시로 주석 처리하는 것은 허용한다.
- 작업 완료 전 불필요하게 주석 처리된 코드는 제거한다.
- 이전 구현이 필요하면 Git 기록을 활용한다.
- 사용하지 않는 코드를 주석 처리하는 대신 실제로 제거할 때는 변경 영향 범위를 확인한다.

### 02-6. 주석의 정확성 및 유지보수
- 코드 변경 시 관련 주석이 실제 동작과 일치하는지 확인한다.
- 구현과 일치하지 않는 주석은 수정하거나 제거한다.
- 오래된 주석을 유지하기 위해 실제 코드의 동작을 임의로 변경하지 않는다.
- 주석에 작성된 설명만으로 기능 구현 여부를 판단하지 않는다.
