# 아키텍처 설계

## 04. 아키텍처 설계

### 04-1. 책임 중심 클래스 분리
- 클래스는 책임을 기준으로 분리한다.
- 서로 다른 이유로 변경되거나 독립적인 기능일 때 분리를 검토한다.
- 단순한 기능을 과도하게 세분화하지 않는다.

### 04-2. 의존성 참조
- 같은 GameObject의 컴포넌트는 `GetComponent`를 활용한다.
- 다른 GameObject 참조는 기본적으로 `[SerializeField]`로 Inspector에서 연결한다.
- 반복 사용하는 컴포넌트 참조는 필드에 캐싱하여 재사용한다.
  - 캐싱은 `private void CacheComponents()` 메서드로 분리하고 `Awake`에서 호출한다.
  - `Awake`가 `CacheComponents()` 호출만 하면 식 본문으로 작성한다. 예: `private void Awake() => CacheComponents();`
  - `Awake`에 다른 초기화가 추가되면 식 본문을 블록 본문(`{ }`)으로 바꾸고, 그 안에서 `CacheComponents()`를 먼저 호출한다.
- 한 번만 사용하는 컴포넌트 참조는 불필요하게 캐싱하지 않아도 된다.
- 매 프레임 `Find` 계열 호출을 지양하고 필수 참조를 검증한다.

### 04-3. 직접 호출과 이벤트
- **동작 요청(Command)**은 직접 메서드 호출을 기본으로 한다.
- **상태 변화 알림(Notification)**은 이벤트를 기본으로 한다.
- 명확한 필요 없이 전역 EventBus를 도입하지 않는다.

### 04-4. Singleton
- 명시적인 참조를 기본으로 하고 Singleton은 최소화한다.
- 실제 전역 시스템이라는 근거가 있을 때만 사용한다.
- 신규 Singleton 도입, 기존 구조의 Singleton 전환은 사전 승인 대상이다.
- 중복 인스턴스 및 `DontDestroyOnLoad` 동작을 고려한다.

### 04-5. 인터페이스·상속·컴포지션
- 실제 공통 계약이 필요할 때 인터페이스를 사용한다.
- 구현을 공유할 필요가 있을 때 추상 부모 클래스를 검토한다.
- 기본적으로 컴포지션을 우선 고려하고, 미래를 예상한 불필요한 추상화는 피한다.
- 공용 API 변경은 영향 범위를 확인하고 사전 승인을 받는다.

### 04-6. 데이터 관리
- 여러 곳에서 재사용하는 공통 설정 데이터는 ScriptableObject를 검토한다.
- 개별 인스턴스의 변경 가능한 런타임 상태는 MonoBehaviour 또는 일반 클래스에서 관리한다.
- 단순 설정은 `[SerializeField]`로 충분하다.
- 공유 ScriptableObject 에셋에 개별 객체의 런타임 상태를 저장하지 않는다.

### 04-7. FSM
- 단순한 상태 전이는 `enum` + `switch`를 사용한다.
- 상태별 로직이 복잡해지면 State 패턴을 검토한다.
- 상태 변경은 `ChangeState` 같은 명확한 진입점을 사용한다.
- 기존 FSM 구조의 대규모 변경은 사전 승인받는다.

### 04-8. 오브젝트 생성 및 풀링
- 생성 빈도가 낮으면 `Instantiate` / `Destroy`를 사용한다.
- 총알·이펙트 등 생성과 제거가 잦은 객체에는 풀링을 검토한다.
- Unity `ObjectPool<T>` 등 적절한 수단을 선택한다.
- 재사용 시 상태 초기화와 중복 반환 방지를 처리한다.
- 기존 생성 구조를 풀링으로 전환하는 구조적 변경은 사전 승인받는다.
