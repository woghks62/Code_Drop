# Unity 개발 규칙

## 05. Unity 개발 규칙

### 05-1. 생명주기 역할
| 메서드 | 주된 역할 |
|---|---|
| `Awake` | 내부 참조 확보 및 자체 초기화 |
| `OnEnable` | 활성화 시 필요한 이벤트 구독 |
| `Start` | 외부 객체와 연계한 초기화 |
| `Update` | 프레임 기반 동작 |
| `FixedUpdate` | 물리 기반 동작 |
| `LateUpdate` | 카메라 등 후처리 |
| `OnDisable` | 이벤트 구독 해제 등 비활성화 정리 |
| `OnDestroy` | 최종 정리 |

- 서로 다른 GameObject의 `Awake` 호출 순서에 의존하지 않는다.
- 위 표는 기본 원칙이며, 실제 구독 수명과 초기화 의존성에 맞춰 조정한다.

### 05-2. 프레임 처리
- 지속적인 Transform 이동·회전은 `Update`를 기본으로 한다.
- Rigidbody 물리 처리는 `FixedUpdate`에서 수행한다.
- 상태 변화에 따른 동작은 가능하면 이벤트로 처리한다.
- 일정 주기의 작업은 타이머나 Coroutine을 검토한다.
- 불필요한 매 프레임 검색·할당을 피하고 성능 문제는 측정 후 판단한다.

### 05-3. Coroutine 및 비동기 처리 — **C. 작업 특성에 따라 선택**
- 프레임마다 수행할 작업은 `Update` 또는 적절한 생명주기 메서드로 처리한다.
- 시간 지연, 순차 연출, 반복되는 게임 동작에는 Coroutine을 검토한다.
- 파일 I/O·네트워크 등 비동기 작업에는 `async/await`를 검토한다.
- 중복 Coroutine 시작을 방지하고 중단·종료 시점을 관리한다.
- `StopAllCoroutines()`의 광범위한 영향에 주의한다.
- `WaitForSeconds`의 `timeScale` 영향을 고려한다.
- `async void`는 가급적 피하고, Unity API의 메인 스레드 제약을 지킨다.
- 기존 비동기 구조의 전면 변경은 사전 승인받는다.

### 05-4. Input System — **C. 프로젝트 특성에 따라 선택**
- 신규 입력은 Unity **New Input System**을 기본으로 한다.
- 간단한 단일 플레이어 입력에는 `InputActionReference`를 검토한다.
- 로컬 멀티플레이어 및 장치별 입력 관리에는 `PlayerInput`을 검토한다.
- 기존 Input Actions 에셋과 입력 구조를 우선 재사용한다.
- 입력 감지와 게임플레이 실행 로직을 가능한 한 분리한다.
- 클릭·드래그 등 입력 구분에는 명확한 판정 기준을 둔다.
- 공유 Input Action의 활성화·비활성화 책임을 명확히 한다.
- 기존 액션 삭제·이름 변경·전면 교체는 사전 승인받는다.

### 05-5. 물리 및 충돌 — **C. 물리 요구사항에 따라 선택**
- 물리 반응이 필요하면 Rigidbody를 사용한다.
- 단순 경로 이동이나 연출은 Transform 이동을 사용할 수 있다.
- 캐릭터 이동 특성에 따라 `CharacterController`를 검토한다.
- Rigidbody 기반 물리 이동은 `FixedUpdate`에서 처리한다.
- 물리 엔진으로 제어하는 Rigidbody를 매 프레임 Transform으로 직접 이동시키는 방식은 지양한다.
- `OnCollisionEnter`와 `OnTriggerEnter`를 용도에 맞게 구분한다.
- LayerMask를 활용하고 레이어 번호를 직접 하드코딩하지 않는다.
- Trigger 이벤트에 필요한 Collider/Rigidbody 구성을 확인한다.
- 2D와 3D 물리 컴포넌트를 혼용하지 않는다.
- 기존 Collider·Rigidbody·Layer 설정 변경 시 영향 범위를 확인한다.

### 05-6. 직렬화 및 Inspector — **C. 설정값과 디버깅 상태 구분**
- Inspector 설정이 필요한 필드만 `[SerializeField] private`로 노출한다.
- 런타임 상태는 기본적으로 일반 `private` 필드로 관리한다.
- 디버깅 상태 표시는 필요할 때 별도 수단을 사용한다.
- Inspector 속성 사용 기준은 `CODE_STYLE.md` 01-11을 따른다.
- Inspector 노출을 위해 무분별하게 public 필드를 사용하지 않는다.
- 기존 직렬화 필드 이름을 함부로 바꾸지 않는다.
- 이름 변경 시 `[FormerlySerializedAs]` 등으로 데이터 보존을 검토한다.
- Prefab·Scene 저장 데이터에 영향을 주는 구조 변경은 사전 승인받는다.

### 05-7. 로그 및 디버깅 — **C. 개발 단계에 따라 로그 관리**
- 개발 중 필요한 임시 디버깅 로그는 허용한다.
- 작업 완료 전 임시 로그를 정리한다.
- 중요한 오류와 경고 로그는 유지한다.
- 정상 동작마다 불필요한 로그를 남기지 않고, `Update`의 반복 로그를 지양한다.
- 로그는 문제의 상황과 원인을 파악할 수 있도록 작성하며 관련 Unity 객체가 있으면 `this`를 전달한다.
- 오류를 감추기 위해 로그만 삭제하지 않는다.

### 05-8. 에셋 참조 및 로딩 — **C. 프로젝트 규모에 따라 선택**
- 일반적인 에셋은 `[SerializeField]`를 통한 Inspector 직접 참조를 기본으로 한다.
- 대량·동적·원격 콘텐츠가 필요하면 Addressables를 검토한다.
- `Resources.Load()`의 무분별한 사용과 경로 문자열 하드코딩을 지양한다.
- Addressables 도입 시 비동기 완료 확인, 로딩 및 해제 책임을 명확히 한다.
- 반복 로딩이 발생하면 캐싱을 검토한다.
- `.meta` 파일과 GUID를 보존해 참조가 깨지지 않도록 한다.
- Addressables 신규 도입 또는 기존 로딩 구조 변경은 사전 승인받는다.

### 05-9. Scene 전환 및 게임 상태 — **C. 프로젝트 복잡도에 따라 선택**
- 단순한 Scene 전환은 `SceneManager` 직접 호출을 허용한다.
- 로딩 화면·비동기 전환·공통 전환 처리가 필요하면 `SceneLoader` 도입을 검토한다.
- Scene 전환과 게임 상태 변경을 구분한다.
- Scene 이름 문자열을 여러 곳에 반복 하드코딩하지 않는다.
- Scene 간 유지 데이터, 참조, 초기화 순서, 이벤트 구독 및 비동기 작업 정리를 확인한다.
- `DontDestroyOnLoad()`는 명확한 필요가 있을 때만 사용한다.
- 기존 Scene의 통합·분리·광범위한 구조 변경은 사전 승인받는다.

### 05-10. 실행 환경 및 플랫폼
- 현재 프로젝트의 대상 플랫폼을 기준으로 기능을 구현한다.
- 지원하지 않는 플랫폼을 위해 불필요한 호환성 코드를 미리 작성하지 않는다.
- 여러 플랫폼을 지원하는 경우 플랫폼별 차이가 있는 기능만 분리한다.
- 플랫폼별 입력 방식, 화면 비율, 해상도 및 성능 제약을 고려한다.
- 플랫폼 종속 API를 사용할 때는 지원 환경을 확인한다.
- 에디터에서의 정상 동작만으로 실제 기기 동작을 보장하지 않는다.
- 대상 플랫폼 변경이나 새로운 플랫폼 지원을 위한 대규모 구조 변경은 사전 승인받는다.

### 05-11. 애니메이션 관리
- 게임플레이 상태와 핵심 판정은 기본적으로 스크립트에서 관리한다.
- Animator는 애니메이션 상태 전환과 시각적 표현을 담당한다.
- 공격 판정 타이밍, 효과음 등 애니메이션과 밀접한 동작에는 Animation Event를 사용할 수 있다.
- Animation Event에서 복잡한 게임 로직을 직접 처리하지 않고 별도 메서드에 위임한다.
- Animator 파라미터는 반복적인 문자열 사용을 피하고 필요하면 해시값으로 관리한다.
- 애니메이션 종료 및 상태 전환 시점을 명확하게 관리한다.
- 기존 Animator Controller의 상태, 파라미터, 전환 조건 변경 시 영향 범위를 확인한다.
- 공용 Animator 구조의 대규모 변경은 사전 승인받는다.

### 05-12. UI 개발
- UI는 정보 표시와 사용자 입력 처리를 담당한다.
- 게임 상태 변경과 핵심 게임플레이 로직은 관련 시스템에 위임한다.
- UI 갱신은 상태 변화 이벤트를 우선 고려하고, 불필요한 매 프레임 갱신을 지양한다.
- UI 구조가 단순하다면 별도의 Presenter나 UI 관리 계층을 강제하지 않는다.
- 버튼 등 UI 이벤트의 중복 등록과 구독 해제를 관리한다.
- 대상 플랫폼의 화면 비율, 해상도 및 Safe Area를 고려한다.
- UI 레이아웃에는 Anchor와 Canvas Scaler를 적절히 활용한다.
- 기존 Canvas 계층, 공용 UI Prefab 및 UI 이벤트 연결 변경 시 영향 범위를 확인한다.
- 공용 UI 구조의 대규모 변경은 사전 승인받는다.

### 05-13. 시간 및 일시정지 관리
- 프레임 기반 동작에는 기본적으로 `Time.deltaTime`을 사용한다.
- 물리 기반 동작에는 `Time.fixedDeltaTime`을 사용한다.
- 일시정지 중에도 진행해야 하는 UI·연출·타이머에는 `Time.unscaledDeltaTime` 등 실제 시간 기준 처리를 사용한다.
- `Time.timeScale` 변경이 물리, 애니메이션, Coroutine 등에 미치는 영향을 고려한다.
- 일시정지 상태와 게임 진행 상태를 명확히 구분한다.
- 여러 시스템에서 `Time.timeScale`을 변경해야 한다면 변경 책임을 한곳에서 관리하는 구조를 검토한다.
- 시간 지연에는 `WaitForSeconds`와 `WaitForSecondsRealtime`을 목적에 맞게 사용한다.
- Scene 전환이나 게임 재시작 시 변경된 `Time.timeScale`의 복원 여부를 확인한다.
- 기존 시간 관리 구조의 대규모 변경은 사전 승인받는다.
