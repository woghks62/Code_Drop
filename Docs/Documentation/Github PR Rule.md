# Github PR 작성 규칙

> Github Pull requets를 작성할 때의 규칙.
>
> PR 작성 양식은 `Docs\Template\PR Template.md`를 참고.
>
> 해당 문서는 각 섹션에 대한 작성 규칙을 정의한다.

## 1. Title

- `[변경 유형] 기능명` 형식으로 작성한다.
- 변경 유형은 작업의 주요 목적에 따라 하나만 선택한다.
- 기능명은 변경 사항의 핵심을 간결하게 표현한다.
- 불필요한 수식어나 상세 구현 과정은 제목에 포함하지 않는다.
- 변경 유형은 아래 항목 중 하나를 사용한다.
  - `Feat` : 새로운 기능 추가
  - `Fix` : 버그 수정
  - `Docs` : 문서 추가 및 수정
  - `Improve` : 기존 기능 개선
  - `Art` : 그래픽 및 에셋 관련 작업
  - `Refactor` : 기능 변경 없는 코드 구조 개선
  - `Chore` : 설정, 패키지 및 기타 유지보수

- 예시 :
  ```markdown
  - [Feat] 플레이어 이동 구현
  - [Fix] 몬스터 피격 판정 오류 수정
  - [Improve] 플레이어 이동 로직 개선
  - [Refactor] Weapon 클래스 구조 개선
  - [Chore] Unity 패키지 설정 변경
  ```


## 2. 관련 Issue

- PR과 연관된 Github Issue 번호를 기재한다.
- Issue의 완료조건(DoD) 충족 여부에 따라 `Refs` 또는 `Closes`를 구분하여 사용한다.
  - `Refs #번호` : Issue의 일부 작업만 완료했거나 완료조건을 모두 충족하지 못한 경우.
  - `Closes #번호` : Issue의 모든 완료조건을 충족하여 해당 PR로 작업이 완료되는 경우.
- 완료조건을 실제로 검증하지 않았다면 임의로 완료 처리하지 않는다.
- 하나의 PR이 여러 Issue와 연관된 경우, 각 Issue의 완료 여부를 개별적으로 판단하여 기재한다.
- 관련 Issue가 없는 경우 임의로 생성하거나 번호를 작성하지 않고 사용자에게 확인한다.
- 예시 :
  ```markdown
  - Refs #12
  - Closes #13
  ```

## 3. 변경 내용 및 목적

- PR에서 실제로 구현하거나 수정한 핵심 내용과 변경 목적을 기재한다.
- 관련 Issue의 `배경 / 목적`, `목표 (To-be)`를 참고하되, 실제 변경된 코드를 기준으로 작성한다.
- 각 변경 사항에 대해 무엇을 변경했으며, 왜 변경했는지 작성한다.
- 주요 처리 흐름이나 설계상 결정이 있는 경우, 해당 구현 방식을 함께 기재한다.
- 단순한 코드 구현 과정이나 불필요한 기술적 설명은 생략한다.
- 리스트로 작성하며, 불필요한 표현을 제거해 간결하게 작성한다.
- 구현하지 않았거나 변경 여부를 확인하지 않은 내용은 작성하지 않는다.
- 예시 :
  ```markdown
  ## 변경 내용 및 목적

  - `DamageInfo` 구조체 생성
    - 데미지 수치와 공격자 정보를 하나의 데이터로 전달하기 위함
  - `IDamageable.TakeDamage()` 매개변수 변경
    - 개별 공격 정보를 `DamageInfo` 구조체로 통합하여 전달
  - 플레이어 및 몬스터 피격 로직 수정
    - 변경된 인터페이스를 사용하도록 수정
  - 구현 방식
    - 개별 매개변수 대신 `DamageInfo` 구조체를 전달하여 공격 정보 관리 방식 통일
  ```

## 4. 영향 범위 및 연동 사항

- 실제 생성/수정/삭제된 파일과 변경으로 인해 영향을 받는 시스템을 기재한다.
- 리스트로 작성하며, 특정 경로의 파일에 어떤 변경이 이루어졌는지 간결하게 작성한다.
- 공용 인터페이스, 데이터 구조, Scene, Prefab, Inspector 설정 등 다른 기능이나 팀원의 작업에 영향을 주는 변경 사항이 있다면 함께 기재한다.
- 추가 설정이나 연동 작업이 필요한 경우 해당 내용을 기재한다.
- 관련 Issue의 `작업 내용`과 실제 변경 파일을 비교하여, 작업 범위를 벗어난 변경 사항이 있는지 확인한다.
- 작업 범위를 벗어난 파일 변경이 있는 경우, 해당 파일과 변경 이유를 별도로 기재한다.
- Unity Editor 또는 개발 도구가 자동 생성하거나 갱신한 파일 중 작업과 직접적인 관련이 없고 기능에 영향을 주지 않는 변경 사항은 PR 본문에서 제외한다.
- 단, 자동 변경된 파일이라도 프로젝트 설정, 빌드, 기능 동작 또는 팀원의 개발 환경에 영향을 주는 경우 반드시 기재한다.
- PR 본문에서 제외하는 것과 Git 변경 사항에서 제외하는 것은 구분하며, 커밋에 불필요한 파일 변경이 포함되어 있으면 사용자에게 알린다.
- 실제 확인된 영향과 추가 확인이 필요한 사항을 구분한다.
- 연동 사항이나 작업 범위 외 변경 사항이 없는 경우 해당 항목은 생략한다.
- 예시 :
  ```markdown
  ## 영향 범위 및 연동 사항

  - `Assets/Scripts/Gameplay/Player/PlayerController.cs` 수정
  - `Assets/Scripts/Core/IDamageable.cs` 수정
    - `TakeDamage()` 매개변수 변경으로 인터페이스 구현체에 영향
  - `Assets/Scripts/Core/DamageInfo.cs` 생성
  - `Assets/Prefabs/Player/PF_Player.prefab` 수정
  - 연동 사항
    - 다른 `IDamageable` 구현체에 변경된 메서드 시그니처 적용 필요
  ```
## 5. 검증 결과

- 관련 Github Issue의 `완료조건(DoD)` 체크리스트를 원문 그대로 가져온다.
- 각 완료조건에 대해 실제 구현 및 검증 결과를 기준으로 충족 여부를 판정한다.
- 완료조건의 문구를 임의로 수정, 삭제하거나 생략하지 않는다.
- 검증에 성공한 항목만 `[x]`로 표시한다.
- 검증에 실패했거나 검증하지 못한 항목은 `[ ]`로 유지한다.
- 검증하지 못한 항목이 있는 경우, 해당 항목과 미검증 사유를 별도로 기재한다.
- 코드 분석만으로 확인한 결과와 Unity Editor에서 실제 실행하여 확인한 결과를 구분한다.
- 각 완료조건의 충족 여부는 사용자에게 확인받는다. 사용자가 확인하지 않은 항목은 성공으로 판정하지 않는다.
- 모든 완료조건을 충족하더라도 최종 검수 및 PR 승인 여부는 사용자가 판단한다.
- PR은 사용자의 명시적인 승인 없이 병합하지 않는다.
- 여러 Issue가 연결된 경우, Issue별로 완료조건을 구분하여 작성한다.
- 예시 :
  ```markdown
  ## 검증 결과

  - [x] `PlayerController` 객체와 `MonsterController` 객체가 `IDamageable` 인터페이스를 통해서만 데미지 판정을 주고받는다.
  - [x] `IDamageable.TakeDamage(DamageInfo info)` 메서드를 통해 공격 정보를 전달한다.
  - [ ] 공격을 받는 객체에서 `DamageInfo` 구조체의 정보를 받아 로그 출력에 성공했다.
  - [ ] Unity Editor에서 컴파일 에러 및 Error, Warning 로그가 발생하지 않는다.

  ### 미검증 항목 및 사유

  - 피격 로그 출력: Unity Editor에서 실제 피격 테스트를 수행하지 못함.
  - Unity Console: 사용자 확인 전
  ```

## 6. 남은 작업 및 주의 사항

- PR 작성 시 미완료 작업 및 알려진 문제를 기재한다.
- 아래 사항 중 하나라도 해당하는 경우에만 해당 섹션을 작성하며, 해당 사항이 없으면 생략한다.
  1. 구현이 완료되지 않았거나 추가 작업이 필요한 경우.
  2. 오류 또는 예상과 다른 동작이 확인된 경우.
  3. 관련 Issue의 `완료조건(DoD)` 중 충족하지 못한 항목이 있는 경우.
- 미완료 작업과 알려진 문제를 구분하여 리스트로 작성한다.
- 미완료 작업은 이후 수행해야 할 작업을 구체적으로 기재한다.
- 알려진 문제는 실제 확인된 현상과 영향을 기재하며, 확인되지 않은 문제를 발생한 사실처럼 작성하지 않는다.
- `5. 검증 결과`에서 기재한 미검증 사유는 중복 작성하지 않되, 후속 작업이 필요한 경우 해당 내용을 기재한다.
- 불필요한 표현을 제거하고 간결하게 작성한다.
- 예시 :
  ```markdown
  ## 남은 작업 및 주의 사항

  - 미완료 작업
    - 몬스터 피격 로그 출력 테스트 필요
    - 다른 `IDamageable` 구현체 연동 작업 필요
  - 알려진 문제
    - 일부 몬스터에서 피격 시 데미지가 중복 적용되는 현상 발생
  ```

## 7. 리뷰 요청 사항

- PR 검토 시 리뷰어가 중점적으로 확인해야 할 코드 및 기능을 기재한다.
- 아래 사항 중 하나라도 해당하는 경우에만 해당 섹션을 작성하며, 해당 사항이 없으면 생략한다.
  1. 코드 구조, 설계 또는 구현 방식에 대한 검토가 필요한 경우.
  2. Unity Editor에서 실제 기능 동작 확인이 필요한 경우.
  3. 사용자가 검증하지 못해 리뷰어의 추가 확인이 필요한 경우.
- 코드 검토와 기능 검증 요청을 구분하여 리스트로 작성한다.
- 코드 검토 요청은 확인이 필요한 클래스, 메서드 또는 설계 내용을 구체적으로 기재한다.
- 기능 검증 요청은 확인해야 할 동작과 예상 결과를 기재한다.
- 별도의 재현 절차가 필요한 경우, 실행 환경 및 테스트 방법을 추가로 기재한다.
- 리뷰에 필요한 실행 화면, 영상, 로그, 관련 문서 등이 있는 경우 참고 자료를 함께 기재한다.
- 실제 존재하거나 접근 가능한 자료만 첨부하며, 존재하지 않는 자료나 링크를 임의로 작성하지 않는다.
- `5. 검증 결과` 및 `6. 남은 작업 및 주의 사항`의 내용을 단순 반복하지 않고, 리뷰어가 수행해야 할 확인 사항을 중심으로 작성한다.
- 실제 확인하지 않은 동작을 정상 작동한다고 단정하지 않는다.
- 불필요한 표현을 제거하고 간결하게 작성한다.
- 예시 :
  ```markdown
  ## 리뷰 요청 사항

  - 코드 검토
    - `DamageInfo` 구조체의 데이터 구성 및 전달 방식 검토
    - `IDamageable.TakeDamage()` 인터페이스 변경 방식 검토
  - 기능 검증
    - Unity Editor에서 플레이어 및 몬스터 피격 동작 확인
    - 피격 시 `DamageInfo` 데이터가 정상적으로 전달되는지 확인
  - 참고 자료
    - 피격 동작 테스트 영상: 첨부 영상
    - `DamageInfo` 전달 과정의 Console 로그: 첨부 로그
  ```
