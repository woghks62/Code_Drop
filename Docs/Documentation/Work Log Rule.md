# Work Log 작성 규칙

> 개인 작업 일지(Work Log)를 작성할 때의 규칙.
>
> 작업 일지 작성 양식은 `@Docs\Template\Work Log Template.md`를 참고.
>
> 해당 문서는 각 섹션에 대한 작성 규칙을 정의한다.

## 1. 날짜 / 작성자

- 작업을 진행한 날짜와 작성자를 기재한다.
- 날짜는 `YYYY-MM-DD` 형식으로 작성한다.
- 날짜 및 작성자 아래에 금일 진행한 핵심 작업을 한 줄로 요약한다.
- 여러 작업을 진행한 경우 주요 작업을 중심으로 작성한다.
- 예시 :
    ```markdown
    ## 날짜 / 작성자
    - 2026-11-05 / woghks62

    - 플레이어 이동 및 카메라 회전 기능 구현
    ```

## 2. 금일 작업 내용

- 금일 실제로 진행한 작업을 기재한다.
- 기능 또는 작업 단위로 구분하여 리스트로 작성한다.
- 단순히 작업명을 나열하지 않고, 어떤 기능을 어떤 방식으로 구현하거나 변경했는지 기재한다.
- 주요 구현 방식이나 설계 변경이 있었다면 해당 방식을 선택한 이유를 함께 기재한다.
- 진행 중인 작업은 항목 끝에 `(진행 중)`을 표시한다.
- 진행 중인 작업에서 남은 세부 작업은 `4. 남겨둔 일`에만 기재한다.
- 불필요한 표현을 제거해 간결하게 작성한다.
- 예시 :
    ```markdown
    ## 금일 작업 내용

    - `PlayerMovement` 생성
      - `CharacterController`를 이용한 WASD 이동 구현
      - `ClampMagnitude(1)`을 적용하여 대각선 이동 속도 보정
    - `PlayerLook` 생성
      - 마우스 입력을 이용한 카메라 회전 구현
      - 카메라 상하 회전 각도 제한
    ```

## 3. 막히거나 헤매었던 부분

- 작업 중 발생한 오류, 예상과 다른 동작, 구현 과정에서의 어려움을 기재한다.
- `문제 상황 → 원인 → 해결 과정 → 결과` 순서로 작성한다.
- 원인을 확인하지 못한 경우 추측으로 단정하지 않고 확인된 사실만 기재한다.
- 해결하지 못한 문제도 현재까지 시도한 내용과 함께 기재한다.
- 관련 오류 메시지나 코드가 필요한 경우 해당 내용을 포함한다.
- 문제가 발생하지 않았다면 `없음`으로 작성한다.
- AI가 작성하는 경우, 작성 전에 사용자에게 막히거나 헤매었던 부분이 있었는지 질문한다.
  - 사용자가 해당 부분을 말하면 그 내용을 기재한다.
  - 사용자가 없다고 답하면, AI가 대화 내용이나 Git 기록을 바탕으로 사용자가 작업 중 헤매었다고 판단한 부분을 제시하고 다시 확인한다.
  - 그래도 사용자가 없다고 답한 경우에만 `없음`으로 작성한다.
- 예시 :
    ```markdown
    ## 막히거나 헤매었던 부분

    - 대각선 이동 시 이동 속도가 증가하는 문제
      - 원인 : 입력 벡터의 크기가 1을 초과
      - 해결 : `Vector2.ClampMagnitude(1)` 적용
      - 결과 : 대각선 이동 속도가 다른 방향과 동일하게 유지됨
    ```

## 4. 남겨둔 일

- 금일 작업 중 완료하지 못한 작업이나 추가 확인이 필요한 사항을 기재한다.
- 추가 구현, 수정, 테스트, 검토가 필요한 항목을 포함한다.
- 완료한 작업은 기재하지 않는다.
- 작업 단위별로 리스트로 작성한다.
- 남겨둔 작업이 없다면 `없음`으로 작성한다.
- 예시 :
    ```markdown
    ## 남겨둔 일

    - 플레이어 이동 중 벽 충돌 동작 검증
    - 카메라 회전 감도 설정 기능 추가
    ```

## 5. 내일 할 일

- 다음 작업일에 진행할 예정인 작업을 기재한다.
- `4. 남겨둔 일` 중 다음 작업일에 수행할 항목을 포함할 수 있다.
- 우선순위가 높은 작업부터 리스트로 작성한다.
- 단순히 `기능 구현`과 같이 포괄적으로 작성하지 않고 구체적인 작업 단위로 기재한다.
- 작업 계획이 정해지지 않았다면 `미정`으로 작성한다.
- 예시 :
    ```markdown
    ## 내일 할 일

    - 플레이어 이동 중 벽 충돌 동작 테스트
    - 카메라 감도 조절 기능 구현
    - 플레이어 상호작용 시스템 설계
    ```

## 6. 금일 커밋 / PR

- 금일 생성한 Git 커밋과 GitHub Pull Request를 기재한다.
- 커밋은 실제 커밋 메시지를 기준으로 작성한다.
- PR은 제목과 번호를 기재하며, 가능하면 링크를 포함한다.
- 관련 Issue가 있는 경우 Issue 번호를 함께 기재할 수 있다.
- 커밋과 PR을 생성하지 않았다면 `없음`으로 작성한다.
- 실제 생성하지 않은 커밋이나 PR을 임의로 작성하지 않는다.
- 예시 :
    ```markdown
    ## 금일 커밋 / PR

    - Commit : [feat] 플레이어 이동 및 카메라 회전 구현
    - PR : #12 플레이어 이동 및 카메라 회전 구현
    - 관련 Issue : #3
    ```

## 7. 개인 회고록

- 금일 작업 과정에서 느낀 점, 새롭게 알게 된 내용, 개선할 점 등을 기재한다.
- 단순히 작업 내용을 반복하지 않고 작업을 통해 얻은 경험을 중심으로 작성한다.
- 작업 중 어려웠던 부분이나 아쉬웠던 점을 자유롭게 작성할 수 있다.
- 불필요하게 긍정적인 표현이나 과장된 평가를 사용하지 않는다.
- 개인 회고는 작성자의 실제 생각과 경험을 기반으로 작성한다.
- AI가 작성하는 경우 사용자의 감정, 생각, 학습 경험을 임의로 추측하여 작성하지 않는다.
- 사용자가 회고 내용을 제공하지 않았다면 해당 섹션을 비워둔다.
- 예시 :
    ```markdown
    ## 개인 회고록

    - 대각선 이동 시 속도가 빨라지는 이유를 처음에는 이해하지 못했다.
    - 입력 벡터의 크기가 이동 속도에 영향을 준다는 것을 알게 되었다.
    - 다음에는 이동 기능 구현 시 방향별 속도도 함께 확인해야겠다.
    ```

## 8. 기타

### 작성 기준

- 모든 내용은 실제 수행한 작업 및 확인된 결과를 기준으로 작성한다.
- Git 기록이나 코드 변경 사항을 참고할 수 있으나, 코드 변경만으로 실제 동작이 검증되었다고 판단하지 않는다.
- 확인되지 않은 작업 결과나 테스트 내용을 임의로 작성하지 않는다.
- 동일한 내용을 여러 섹션에 불필요하게 반복하지 않는다.
- 코드, 클래스, 메서드, 파일명 등은 백틱(`)으로 감싸 작성한다.
- 각 항목은 리스트 형식을 기본으로 사용한다.
- 장황한 설명보다 핵심 내용과 판단 근거를 우선하여 작성한다.

### 파일 위치

- 작업 일지는 `Docs\WorkLog\` 폴더에 저장한다.
- 파일 이름은 `YYYY-MM-DD.md` 형식으로 한다. (예: `2026-11-05.md`)
- 같은 날짜의 파일이 이미 있으면 새로 만들지 않고 기존 파일에 내용을 추가·수정한다.
